# Consensus 발표 시나리오

> 형식: 발표자가 없어도 심사위원이 자료만 읽고 이해할 수 있는 제출용 서사  
> 핵심 메시지: **Consensus는 결정을 대신하지 않는다. 팀의 결정이 어떤 조건에서 깨지는지 보여준다.**

## 구성 원칙

- 각 페이지가 발표자 설명 없이 하나의 결론을 전달한다.
- 라이브 데모나 네트워크 연결을 전제로 하지 않는다.
- 수치는 실제 `demo_data.json`과 `/analysis` 결과만 사용한다.
- 기술 구조는 구현 세부사항보다 신뢰 경계를 중심으로 설명한다.
- 공격 테스트는 기능 목록이 아니라 제품 신뢰의 증거로 제시한다.

## 전체 서사

| 단계 | 심사위원이 갖게 되는 질문 | 자료가 제공하는 답 | 핵심 증거 |
|---:|---|---|---|
| 1. 문제 | 만장일치인데 무엇이 문제인가? | 표면적 합의는 말하지 않은 우려를 제거한다. | A에 4명 동의했지만 구현 우려 반복 |
| 2. 접근 | 기존 투표와 무엇이 다른가? | 익명 입력을 통계적으로 스트레스 테스트한다. | 익명 입력 → 통계 → 반론 질문 |
| 3. 결과 | 실제로 다른 결론이 나왔는가? | 말로는 A였지만 익명 입력과 안정성은 B를 가리켰다. | B 75%, Stability 82.2% |
| 4. 취약 조건 | 그 결과는 무조건 맞는가? | 발표 임팩트 가중치가 +8%p면 A로 뒤집힌다. | Flip Point +8%p |
| 5. AI 역할 | AI가 결정을 대신하는가? | AI는 약한 가정을 질문할 뿐이다. | Devil's Advocate 질문 2개 |
| 6. 신뢰 | LLM이 숫자를 조작할 수 있는가? | GPT와 numpy의 책임을 분리했다. | 범주형 구조화와 결정적 계산 분리 |
| 7. 검증 | 비정상 입력에서도 안전한가? | 5개 공격 시나리오가 기대 동작을 통과했다. | 13 tests passed |
| 8. 실증 | 팀이 실제로 사용했는가? | 제품 선택 자체에 Consensus를 사용했다. | A → 검증 → B |
| 9. 결론 | 어디에 적용할 수 있는가? | 소수가 고비용 결정을 내리는 모든 장면에 적용 가능하다. | 채용·투자·제품 우선순위 |

## 페이지별 읽기 흐름

### 1. 문제를 자신의 경험으로 인식

심사위원은 “회의에서는 모두 동의했지만 실행 단계에서 반대가 나오는 상황”을 즉시 떠올릴 수 있어야 한다.

> 만장일치라는 한 숫자가 중요한 차이를 지웠습니다.

### 2. 제품이 결정을 대신하지 않는다는 점 이해

제품은 추천 엔진이 아니라 결정의 견고성을 측정하는 도구임을 분명히 한다.

> 판단은 팀에 남기고, 판단의 조건만 드러냅니다.

### 3. 실제 데이터로 효과 증명

가상의 마케팅 숫자가 아니라 팀의 실제 입력과 API 분석 결과를 사용한다.

- B 익명 1순위: 75%
- B Decision Stability: 82.2%
- 발표 임팩트 Flip Point: +8%p

### 4. Devil's Advocate로 정성적 취약점 제시

> 핵심 기능이 완성되지 않을 때 무엇을 남기고 무엇을 버릴 건가요?

> 구현 가능성 우려를 해소했다고 판단할 최소 검증은 무엇인가요?

### 5. 기술적 신뢰 확보

- GPT: 선호 옵션, 긍정 기준, 우려 기준 구조화
- numpy: Stability, Flip Point, Robust Choice 계산
- 팀: 결과를 해석하고 최종 결정

### 6. 공격 테스트로 신뢰 증명

“정상 흐름이 동작한다”보다 “실패 조건에서 어떻게 동작하는가”를 제시한다. 빈 입력, 제출 0건, 완전 동점, 1명 제출, 프롬프트 인젝션을 통해 통계 엔진과 LLM 경계의 안전성을 보여준다.

### 7. 제품 자체가 첫 적용 사례임을 제시

말로 합의한 A 대신, 익명 입력과 스트레스 테스트 결과가 더 견고한 B를 가리켰고 그 B가 Consensus라는 순환 구조로 마무리한다.
